## 会话存档（P0）

- 一段对话 = 一个存档；`dates[]` 是真相，`bindings` 派生；
- 一档可多天，一天可多档；
- 新建走客户端 `sessions.create({cwd})` → `POST /api/saves` → `openSession` → `requestDraftInitialization` 预填；
- 读取旧档只打开、不预填；「回到对话」只 closePanel；
- 日记 frontmatter 不加 sessionId；
- P2 已实现（v0.6.1）：自动 seal、逐档管理、未绑定列表刷新；书页 badge 与今天页 chip 沿用 P0 实现。

## 关键决策

1. 文件是唯一数据源；git 是回退，不是存储。
2. 书房写日记，房间只写房间日志；房间不写日记已做成工具层硬锁（v0.6.2，判不出时放行）。
3. 先草稿后定稿；`diary_write` 默认 draft。
4. 人设图只给界面，模型拿文字自述。
5. 技能按 workspace 放（`diary-ritual`/`room-chat` 只在 `/sdcard/diary-vault` 出现）。
6. 工具自己写 ToolDefinition，不引入 `dsh-tools`，避免 link 依赖。
7. 存档表 `.diary/saves.json` + gitignore；不写进日记。
8. 工作区不自动创建，避免空白座位会话；用户手动选择。

## 已知问题 / 风险

- **客户端热更新不一定生效**：大改后要强制刷新页面；面板「设置 → 面板版本」应显示 `v0.6.3 · 2026-10-26.5`。
- **DSH 空工作区座位**：打开空工作区会建一个空白会话；这是 DSH 行为。测试留下的空会话还在，可手动归档；不要程序化删 `~/.dsh/sessions`。
- **房间不写日记已做成硬边界**（task-2）：房间会话调 `diary_write(kind='diary')` 直接报错、不落盘；`maid`/`profile` 仍可用，书房行为不变。
  判定不靠提示词，靠会话自己的持久事件日志：`tool/call` 里加载过的 `room-chat`/`diary-ritual`、`room_log` 调用、`session/title`（房间日志会改名为「房间 · …」）。
  DSH 没有可改写的「会话模式」字段（`SessionHeader` 只有 cwd/父会话/预设等创建元数据，创建后冻结），所以只能读日志；判不出来时**按书房放行**（宁可少拦），进程内 warn 一次。
- **侧写可只增追加**（task-2）：新工具 `profile_append({ section?, entries:[{ text, kind:'fact'|'guess', date? }] })`，旧正文逐字节保留、幂等去重、覆盖前快照 + git commit、串行化；`diary_write(kind='profile')` 整篇写仍保留，但描述里优先推荐 append。
- **自动 seal 已接**（v0.6.1）：`diary_write` final 与 `PUT /api/entry` final 都会收当天所有 active 档；失败只 warn。
- **未绑定会话列表**是打开抽屉时的快照；抽屉内可手动「刷新列表」，不自动轮询。
- **UI 未逐项真机验证**：抽屉/切换/管理页/失败态、房间改名/归档/恢复、360–430px 窄屏观感需要用户点。
- **`PUT /api/sessions` 已返回真实结果**（v0.6.3）：成功 `renamed:true`，失败 200 + `renamed:false` + error；`room_log` 内部顺带改名仍吞错（日志不该因改名失败而失败）。
- **测试偶发 14/15** 曾出现，现串行 62 条稳定；若再出现记到 bug 台账。
- 代码仓工作区有别人留下的未提交 `README.md` 删除行、`docs/路线图.md` 删除；不要 revert，等 owner。

## 新会话开场：先建团队，再干活

旧团队和任务板**不会跟着新对话走**。新 Lead 按这个顺序做：

1. 读 `docs/产品需求.md`、本文件、`docs/任务板-第一阶段.md`、`docs/会话存档设计.md`。
2. `team_task_create` 重建 **1–2 条**最重要的任务（建议：功能包里的一项，或人设真实验收后的修订）；不要一次把旧板全抄。
3. `spawn_teammate` 拉 **1–2 个**成员，各自认领一条；写作用域别重叠（一个 host、一个前端最稳）；
   人设 v4 由 Lead + 用户做，不外包；bug 需要时再拉一个。
4. 成员只改自己任务写作用域里的文件；Lead 验收、跑测试、提交。
5. 不要同时开 3 个以上；成本敏感。
